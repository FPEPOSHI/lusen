Lusen

API documentation for Laravel that people, search engines and AI agents can all read.

Lusen reads your application's routes, form requests and resources and writes the documentation as static files: HTML for people, Markdown and OpenAPI for machines, llms.txt for retrieval models, and an MCP server for agents. No configuration, no database, and no JavaScript needed to read a page.

View the example GitHub

Install

composer require fpeposhi/lusen
php artisan lusen:build

That is the whole setup. Lusen discovers api/* routes and documents them with no configuration, writing to public/docs so your web server serves the result as flat files with no PHP on the request path.

Three readers

People
Server-rendered HTML, one page per endpoint and one per group, readable with JavaScript disabled. Request examples in six languages, search that needs no server, and an optional playground.
Search engines
Canonical URLs, real meta descriptions, JSON-LD and a sitemap. One page per question, so nothing competes with itself.
AI agents and generative search
A Markdown twin of every page — swap .html for .md — plus llms.txt, OpenAPI 3.1, a discovery document at /.well-known/api-docs, and an MCP server that answers with the same Markdown a person reads.

The example

Everything under /example/ was written by Lusen's own emitters over a fictional commerce API: {{endpoints}} endpoints across {{groups}} groups, two versions served at once with v2 current and v1 deprecated. Nothing there is a mockup. Some places to look:

  • An endpoint page — the reference on the left, the call on the right, and Changed since v1 worked out by comparing the two editions.
  • A group page — what can be done with orders, before any one operation.
  • The versioning page — written by Lusen from what the two versions actually expose.
  • The same endpoint as Markdown, openapi.json and llms.txt.
  • How these docs are built — the three stages, and the example folder that produced the site.

What it works out on its own

  • Request bodies from form request rules, including nested items.*.product_id shapes.
  • Response fields from API resources, typed from model casts and migrations.
  • Authentication and scopes from middleware, and rate limits from throttling.
  • API versions from URLs: which is current, which are deprecated, and which operation supersedes which.
  • Real response examples recorded from your test suite, and a contract diff that grades each change by what it costs a client.

Where inference stops, attributes and docblocks have the last word, including the ones another tool left behind. Extraction is static analysis: a build never boots the application, so it runs in CI against a checkout with no .env.
